And on further looking into the json file with this "singularity" string, I found, ==**singularity.ko**==, (KO=Kernel Object). And it confirms that it is the hidden kernel module.

> [!Info] Info
> **Singularity** is a highly sophisticated, open-source Linux Kernel rootkit designed for the modern Linux kernels, version 6.x.


Based on the output and its taint flag set for the module, it shows that the module is the rootkit, because in forensics we use this flags and determine it is the suspicious module and it doesn't belong on a clean system.

The two flags are:
- `OOT_MODULE (OUT-Of-Tree):` It means, this module was compiled outside of the official Linux kernel source code tree. 
	- `Why it matters?:` Official drivers (like standard file drivers, or network drivers) are built directly alongside the kernel source code. *Out-Of-Tree* module means someone wrote or downloaded separate C code, compiled it independently into `.ko` file and injected it later.
- `Unsigned_Module:` It means, the `.ko` file lacks a cryptographically valid signature from the OS.
	- The secure Linux systems uses cryptographic signatures to ensure that only verified, trusted drivers are allowed to execute in Ring 0 (Kernel Space). 
	- So it confirms that binary did not come from an official package repository or a trusted vendor, it is completely untrusted code.


The loaded time for this rootkit can be identified using the ==kmsg== plugin from volatility. This plugin extracts the kernel log messages along with their precise kernel uptime records.
```python3
python3 vol.py -s <directory_location_for_json/dir/> -f dump_srv.mem linux.kmsg.Kmsg | grep "singularity" 
```

While investigating file using ==strings== tool, I captured the list of important strings from the mem.

<img class="zoomable" src="/assets/Phantom/5.png" alt="image5">

These two important syscall are important as they represent the Kernel Tracepoint Hook. 
*A kernel tracepoint is a specific internal kernel tracing event or mechanism the rootkit intercepted to run its own code secretly*. 

Those two syscall proves that:
- Instead of using standard syscall table hooking, *singularity* called `tracepoint_probe_register()` to attach its payload to `__tracepoint_sched_process_fork` (event name: **sched_process_fork**)
- Every time a process forks a child, this trace-point triggers, executing the rootkit's privilege escalation routine defined in `/root/Singularity/modules/become_root.c`


> [!Info] Info
> In the Linux kernel, `sched_process_fork` is a built-in kernel tracepoint that triggers whenever a process creates a new child process using the `fork()`, `vfork()`, or `clone()` system calls
